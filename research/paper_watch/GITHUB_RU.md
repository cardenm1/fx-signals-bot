# GBP/USD Strategy v1.0 — GitHub Paper Watch

**Статус: подготовлено локально. Автоматический запуск и Telegram выключены.**

Модель распознавания остаётся исходной строгой D1 → H1 → M5. Это отдельный модуль, а не замена `bot.py`. Версия v1.0 работает в режиме **SIGNAL_ONLY**: формирует подтверждённые демосигналы и ориентиры SL/TP, но не открывает даже виртуальные позиции. Реальных ордеров, подключения торгового счёта, брокерского SDK или учётных данных счёта нет.

## Что входит

- `.github/workflows/paper-watch-v1.yml`: ручной запуск `self-test` или `observe`; единственный активный trigger — `workflow_dispatch`.
- `github_runner.py`: один ограниченный сбор данных, максимум 12 запросов по 6 часов покрытия за запуск, обработка закрытых M5, догрузка от последней сохранённой свечи.
- `state_store.py`: отдельная ветка `paper-watch-state-v1` как основное постоянное хранилище. Артефакт — только диагностическое дополнение.
- `telegram_outbox.py`: отдельный отключённый по умолчанию этап публикации PAPER.
- `test_github.py`: офлайн-тесты восстановления, хранения и уведомлений. Внешний Telegram при тестах не вызывается.

## Неизменённая модель

D1 — граница 00:00 UTC, направление по структуре подтверждённых swing 2/2; важная зона от первого swing и двух реакций с прежними допусками и сроком 60 активных D1. H1 — закрытие за зоной по тренду. M5 — снятие ликвидности и возврат в той же свече, затем отдельное закрытие за фиксированным BOS. Варианты EMA220, динамического BOS и ретеста не включены. Проверка SHA256 замороженного распознавателя и плана остаётся обязательной.

Вход в сообщении — **ориентир по цене сигнального закрытия**, а не исполнение. BUY использует ASK, SELL — BID; структурный SL берётся по исходному правилу, TP — 2R от ориентира. Отклонение `SIGNAL_ONLY_NO_EXECUTION` означает только отключённое виртуальное исполнение; оно не отменяет подтверждение самой модели.

## Постоянное состояние и восстановление

В state-ветке находятся `deployment.json`, `status.json`, папка `session/` с прогревом BID/ASK, первичным `events.csv`, CSV-представлениями, исходными пакетами тиков и `session/notifications/events.csv`. Токен и chat ID сюда не попадают. В публичном репозитории эта ветка и рыночные журналы тоже будут публичными.

Один workflow держит общую concurrency-группу. Git push выполняется без force; устаревший параллельный писатель не может затереть новое состояние. Отсутствие ветки состояния вызывает ошибку, а не тихую повторную инициализацию. Повреждённый первичный журнал не загружается обратно в GitHub.

`ANALYSIS_CHECKPOINT` отделяет сохранённый BAR от успешно завершённого анализа. После сбоя анализ догоняет сохранённые свечи. Между запусками состояние восстанавливается из state-ветки, а не из файлов предыдущей машины runner. При обычной ошибке сбора workflow всё равно пытается сохранить журналы. Если процесс уничтожен до commit/push, следующий запуск повторно получает незакоммиченный диапазон от последней удалённой отметки. Новые сообщения Telegram до сохранения состояния не отправляются.

Сбор начинается с повторной проверки последнего принятого M5. Успешный запрос должен полностью покрывать интервал, а текущие часы должны находиться минимум на две секунды после его закрытия. Первый частичный интервал исключается. BID/ASK, UTC, OHLC, порядок и неизменность принятых баров проверяет существующий Paper Watch.

Если пропущен активный M5, принимается только полный префикс перед разрывом. Записывается `DATA_GAP`, следующий запуск снова начинает с этого места. Искусственных свечей нет. Запланированные выходные определяются по Нью-Йорку 17:00 с DST; D1 при этом остаётся UTC. Неизвестные праздники не считаются автоматически нормальным отсутствием данных. Превышение лимита догрузки даёт `CATCHUP_PENDING`; остаток обрабатывается следующим запуском.

## Подготовка GitHub после согласования изменений

1. Сохраните резервный архив рабочей версии отдельно от репозитория. Не удаляйте старый `bot.py` или старый workflow.
2. Разместите только новый workflow и папку `research/paper_watch/` в проверяемой ветке. Не добавляйте `research/data/`, локальные результаты, резервные архивы, токены или `.env`.
3. Проверьте diff. Для появления кнопки ручного запуска workflow должен существовать в default branch. Публикацию/слияние выполняйте только после согласования. Старый workflow имеет собственное расписание и не отключается этой версией; переключение старого наблюдателя согласуется отдельно.
4. В Settings → Actions → General разрешите запись `GITHUB_TOKEN` для сохранения state-ветки. Только job наблюдения запрашивает `contents: write`; self-test имеет `contents: read` и не получает Telegram secrets.
5. При необходимости создайте environment `paper-watch` с ручным approval и разрешённой веткой развёртывания.
6. Создайте repository variables `PAPER_WATCH_ENABLED=false`, `PAPER_WATCH_TELEGRAM_ENABLED=false`. Эти значения по умолчанию также считаются выключенными, если переменные отсутствуют.
7. Выполните **только** `Run workflow → mode=self-test, publish=false`. Это офлайн-проверка: не собирает рынок, не восстанавливает рабочую сессию и не публикует сообщения. Зафиксируйте URL, commit SHA, итог и журнал настоящего GitHub run.

Сохранённый локальный прогон не заменяет пункт 7. До появления реального run URL нельзя считать GitHub Actions проверенным.

## Первичная инициализация — только после разрешения на наблюдение

Нужна полная актуальная закрытая история для прогрева. Одного года достаточно для воспроизведения зафиксированной модели, но это не независимая проверка. История 2025–2026 ранее исследовалась; старые сигналы не превращаются в forward-сигналы.

Пример команд из корня репозитория, в отдельном Python 3.12 окружении:

```sh
python -m pip install -r research/paper_watch/requirements.txt

# Сетевое пополнение используется только для прогрева, не для публикации.
# Выполнять после разрешения на этот этап; каталоги должны быть новыми.
python -m research.paper_watch.cli bootstrap \
  --bid /path/GBPUSD_BID_M5_CLEAN.csv \
  --ask /path/GBPUSD_ASK_M5_CLEAN.csv \
  --out /tmp/gbpusd-warmup-v1 --approve-paper

python -m research.paper_watch.github_runner seed \
  --root /tmp/gbpusd-seed-v1 \
  --bid /tmp/gbpusd-warmup-v1/GBPUSD_BID_M5.csv \
  --ask /tmp/gbpusd-warmup-v1/GBPUSD_ASK_M5.csv

# GitHub credentials задаются вне кода; значения не печатать и не коммитить.
# GITHUB_REPOSITORY=cardenm1/fx-signals-bot
# GITHUB_TOKEN — через безопасное окружение/менеджер секретов, с доступом Contents write.
python -m research.paper_watch.state_store upload-seed \
  --root /tmp/gbpusd-seed-v1 --confirm-new-state
```

Инициализация устанавливает начало оценки не раньше текущей следующей M5 и 24.10.2026 00:00 UTC. Старый прогрев не анализируется как новый сигнал. Повторная инициализация существующей state-ветки запрещена. Если предоставленный CSV устарел, seed остановится и попросит актуальный прогрев.

После создания state-ветки и отдельного разрешения установите `PAPER_WATCH_ENABLED=true`. Ручной `mode=observe, publish=false` выполнит один ограниченный сбор, сохранит состояние и остановится. Вне торговой недели статус будет `MARKET_CLOSED`; это не успешная проверка живого потока. Для окончательной проверки на открытом рынке нужны отдельные реальные наблюдения нескольких последовательных новых свечей.

## Telegram — только после отдельного подтверждения

1. Добавьте `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` в GitHub Actions Secrets, не в код или state-ветку. Не присылайте токен в чат.
2. Только после подтверждения установите `PAPER_WATCH_TELEGRAM_ENABLED=true`.
3. Выполните ручной `observe` с `publish=true`. Первая активация лишь сохраняет границу публикации: ни один ранее накопленный сигнал не отправляется.
4. Следующие разрешённые запуски рассматривают только сигналы после этой границы, не старше пяти минут, полученные до исходного срока входа. Исторические/задержанные сигналы могут присутствовать в CSV для диагностики, но не отправляются как новые.

Текст содержит `PAPER | DEMO`, версию стратегии, UTC, направление, D1, ориентир входа, структурный SL, TP 2R, спред и постоянный ID. Ни исходный `bot.py`, ни `python-telegram-bot` новый модуль не вызывает.

Перед HTTP-запросом записывается `NOTIFY_INTENT` и сохраняется в удалённой state-ветке. Один ID получает максимум одну автоматическую попытку отправки. При таймауте или обрыве между отправкой и сохранением результата возникает неопределённость: Telegram не предоставляет здесь ключ идемпотентности. Повторная автоматическая отправка запрещена. Состояние `UNKNOWN_NO_RETRY` либо intent без результата требует сверки вручную по ID; сообщение может быть недоставлено. Не удаляйте intent для принудительного повтора без такой сверки.

## Периодический режим — подготовлен, но выключен

После явного подтверждения добавьте в существующий блок `"on"` нового workflow:

```yaml
  schedule:
    - cron: '2-57/5 * * * *'
```

Условия job уже учитывают событие `schedule`, но сейчас такого trigger нет. Переменная `PAPER_WATCH_ENABLED` должна быть `true`; Telegram отдельно требует `PAPER_WATCH_TELEGRAM_ENABLED=true`. Наличие токена само по себе не включает публикацию. Для штатного cron ручной input `publish` не используется.

GitHub Actions не гарантирует точную пятиминутную доставку: запуски могут задерживаться или пропускаться. Это причина наличия догрузки и запрета старых уведомлений, а не обещание доставки всех сигналов в реальном времени.

## Отключение и восстановление старой версии

- Отключить только Telegram: `PAPER_WATCH_TELEGRAM_ENABLED=false`. Дождаться завершения уже работающего publisher либо отменить run, затем проверить его intent/result. Изменение переменной не отзывает уже выполненную отправку.
- Отключить наблюдение: `PAPER_WATCH_ENABLED=false` и Disable workflow у **GBPUSD Strategy v1.0 PAPER**. Уже работающий run при необходимости отменить. После прерывания проверить состояние и notification intents.
- Удалить/закомментировать schedule нового workflow. Сохранить state-ветку и резервную копию; не чистить журналы.
- Старые `bot.py` и `.github/workflows/send-signal.yml` оставлены без изменений. Их включение/отключение — отдельное действие. Если они были отключены при переключении, восстановить через Actions UI после согласования.
- Для отката выбрать **тот же проверенный код релиза**, соответствующий `deployment.json`. При несовпадении хешей система откажется продолжать старую сессию. Не редактировать INIT/хеши для обхода. Обновление стратегии или runtime — отдельная версия и явно согласованная новая сессия/миграция, без стирания старой истории.

## Эксплуатационные ограничения

State-ветка переживает удаление artifacts, но не удаление самой ветки/репозитория. Делайте отдельные резервные копии state-ветки и CSV. В долгом наблюдении Git-история, сырые тики и append-only журналы растут; контролируйте размер ветки, файлов и расход Actions. Для длительного хранения больших объёмов потребуется согласованное архивирование/внешнее хранилище, а не очистка текущих журналов. Плановые выходные не проверяют доступность поставщика в открытый рынок.
