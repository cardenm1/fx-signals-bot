# Liquidity BOS DEMO: запуск и ограничения

Другие стратегии и workflows не изменены. Автоматических сделок нет.

## Проверка в GitHub Actions

После слияния PR откройте Actions → Liquidity BOS DEMO → Run workflow.
1. `mode=self-test`: 24 offline-теста, без секретов и сетевых котировок.
2. `mode=live-data`: реальные BID-тики всех 11 пар, сборка закрытых M1;
   Telegram и состояние не используются. Запускайте при открытом FX-рынке.
3. Задайте repository secrets TELEGRAM_BOT_TOKEN и TELEGRAM_CHAT_ID.
   Токен должен принадлежать отдельному боту: getUpdates нельзя одновременно
   использовать в другом процессе; webhook должен быть удалён заранее.
4. `mode=observe`, `initialize_state=true` только при первом запуске.
   Создаётся отдельная ветка liquidity-bos-state; следующие запуски восстанавливают её.
   Если есть ранее сохранённые уровни, перенесите проверенный JSON в эту ветку
   до observe; автоматического восстановления старого cache/artifact нет.
5. Отправьте боту /add GBPUSD 1.34500, /list, /status, /remove GBPUSD 1.34500.
   Запустите observe повторно с initialize_state=false: ответ придёт после запуска,
   а уровни должны сохраниться в ветке состояния между запусками.
6. Для расписания задайте repository variable LIQUIDITY_BOS_ENABLED=true.
   Без этой переменной расписание выполняет только offline-тесты.
   Отключение: LIQUIDITY_BOS_ENABLED=false.

GitHub Actions бесплатен для стандартных hosted runners публичного репозитория.
При смене видимости действуют квоты аккаунта. Cron каждые 5 минут не гарантирует
точный интервал: GitHub может задерживать/пропускать задания. Права workflow:
contents:write нужны для отдельной ветки состояния; защищающие правила этой ветки
должны разрешать обычный push от GITHUB_TOKEN. Force push не применяется.
Состояние в публичном репозитории публично: JSON содержит уровни и offset,
но не содержит токена или chat ID.

## Проверяемое определение сигнала

За последние 4 часа загружаются реальные Dukascopy тики, BID агрегируется в M1.
Для полноты последней минуты требуется тик из следующей минуты. Синтетические
свечи не создаются. M5 требует ровно пять закрытых M1.

Снятие верхнего уровня: предыдущий high <= уровень, текущий high > уровень;
для нижнего аналогично low. Два направления одновременно неоднозначны и пропускаются.
Возврат закрытия за уровень не обязателен: сохранено исходное определение
пробоя/снятия уровня, поддерживаются продолжение и разворот.
BOS — закрытие через последний уникальный pivot high/low, подтверждённый двумя
свечами справа до BOS-свечи. BOS-свеча должна начаться ПОСЛЕ M1-свечи снятия.
BOS на самой свече снятия и M5, включающая снятие, пропускаются: порядок событий
внутри OHLC неизвестен. На одну установку допускается один сигнал M1 и один M5.
Установка действует 120 минут; новый цикл возможен после истечения срока.
Первый запуск не рассылает историю. Обрабатываются новые свечи не старше 15 минут;
после более долгого простоя старые установки сбрасываются. Пропуски свечей не
используются для подтверждения непрерывной структуры.

## Доставка и ошибки

Перед каждым сигналом идентификатор сохраняется и отправляется обычным push
в ветку состояния. Только затем вызывается Telegram. Повторный запуск не
повторяет такой сигнал даже при неоднозначном сетевом таймауте. Цена этой защиты:
при остановке процесса между записью и доставкой сообщение может потеряться.
Строгое exactly-once Telegram Bot API не предоставляет. В JSON sent означает
зарезервированные попытки доставки, а не подтверждение прочтения/получения.

Команда и offset сохраняются перед ответом. Ошибка ответа не откатывает команду.
/add существующего уровня не сбрасывает установку. Цены округляются до 5 знаков,
для JPY до 3; nan/inf/некорректные пары отклоняются. Доступ ограничен chat ID,
в группах команды могут посылать все участники разрешённого чата.

Неисправный JSON и ошибка восстановления не создают пустую замену состояния.
Ошибка push блокирует отправку. Ошибка одной пары не мешает проверке остальных,
но завершает run с ошибкой; /status показывает последние свечи и ошибки.
Свечи старше 10 минут отклоняются, в том числе на выходных.
Запросы имеют HTTP-таймауты, ограниченные повторы, число страниц и бюджет времени.

## Локальная проверка

Python 3.12:
```
python -m pip install -r requirements-liquidity.txt
python -m unittest discover -s tests -p 'test_liquidity*.py' -v
python liquidity_feed.py
```

24 теста прошли локально; реальные котировки всех 11 пар получены 28.10.2026.
Тесты Telegram используют mock; живой Telegram, repository secrets и выполнение
workflow на hosted runner требуют окончательной проверки по шагам выше.

SDK dukascopy-python больше не требуется этой стратегии: адаптер использует
тот же chart/json3 источник, но явно задаёт таймауты, HTTP-заголовки и валидацию.
Источник API не имеет гарантии доступности; сбои видны в workflow и /status.
