# Liquidity BOS DEMO: ручные уровни и одноразовые M1-сигналы

## Команды и запуск

Сохранены `/add GBPUSD 1.34500`, `/remove GBPUSD 1.34500`, `/list`,
`/status`, `/start`, `/help`. `/list` показывает все регистрации и их состояния,
`/status` — активные уровни, состояния, доставку, последние свечи и ошибки.
Уровень регистрируется один раз; повторный `/add` не сбрасывает его состояние.
Явное `/remove`, затем `/add` создаёт новую регистрацию по той же цене.

Существующие `send-signal.yml`, `paper-watch-v1.yml`, `bot.py` и PAPER-стратегия
не изменены. Реальных ордеров нет. Новая проверка PR запускает только offline-тесты,
без Telegram, рыночных запросов и секретов.

Для существующего workflow Liquidity BOS DEMO:

1. `mode=self-test`: offline-тесты.
2. `mode=live-data`: проверка Dukascopy всех 11 пар без Telegram.
3. Для наблюдения нужны TELEGRAM_BOT_TOKEN и TELEGRAM_CHAT_ID. Токен должен
   принадлежать отдельному боту, без другого getUpdates-процесса и webhook.
4. `mode=observe`, `initialize_state=true` только при первом запуске.
   Последующие запуски используют `initialize_state=false` и отдельную ветку
   `liquidity-bos-state`. Существующую ветку не переинициализировать.
5. Расписание наблюдения включается `LIQUIDITY_BOS_ENABLED=true`.
   Без неё расписание выполняет только offline-тесты.

Используется существующая инфраструктура GitHub Actions публичного репозитория
и Dukascopy; новые платные сервисы не нужны. Расписание раз в 5 минут может
задерживаться. M1 — таймфрейм подтверждения, а не обещание доставки за минуту.
Состояние в публичной ветке содержит уровни и offset, без токена и chat ID.

## Правила сигнала

Используются BID-тики Dukascopy за последние четыре часа. M1 включает только
закрытые минуты; тик из следующей минуты подтверждает завершение предыдущей.
Отсутствующие минуты не заполняются синтетическими свечами.

Первое событие — строгий выход за установленный уровень:

- вверх: предыдущий high <= уровень, текущий high > уровень;
- вниз: предыдущий low >= уровень, текущий low < уровень.

Касание не является выходом. Неоднозначный выход одновременно в обе стороны
пропускается. Свечи, начавшиеся до регистрации уровня, не используются для выхода.

После выхода бот ждёт первый BOS на последующей закрытой M1-свече, в любую сторону.
BOS вверх — переход закрытия через последний уникальный pivot high; вниз —
через pivot low. Pivot имеет две свечи слева и две справа, причём обе правые
свечи закрыты ДО BOS-свечи. Тень за структурным экстремумом без закрытия не подходит.
Свеча выхода не может одновременно стать BOS: порядок внутри OHLC неизвестен.
M5-уведомления в этой стратегии больше не формируются.

В уведомлении отдельно указываются:

- **снятие с возвратом за уровень**: хотя бы одна закрытая M1 после выхода,
  включая саму свечу выхода и свечу BOS, закрылась строго обратно за уровень;
- **пробой без возврата**: до BOS включительно такого закрытия не было.

Касание уровня закрытием и внутриминутная тень не подтверждают возврат.
Признак возврата сохраняется, даже если затем цена снова уйдёт за уровень.

| Первый выход | BOS вверх | BOS вниз |
|---|---|---|
| Вверх | Продолжение | Разворот |
| Вниз | Разворот | Продолжение |

## Состояния и неполная история

`watching` → `waiting_bos` → `completed`.
После первого сигнала регистрация остаётся завершённой навсегда, в том числе
после перезапуска, повторного выхода, истечения 120 минут и очистки старого журнала.
Незавершённое ожидание BOS старше 120 минут получает терминальный статус `expired`.
Автоматического повторного запуска нет.

Перед анализом проверяются время, порядок, уникальность, закрытие свечей,
конечные положительные цены и согласованность OHLC. Для структуры используется
только непрерывный минутный участок. Пропуск минуты после регистрации или потеря
необходимой истории выхода/BOS переводит уровень в `incomplete_history`.
В частности, checkpoint старше доступного окна не позволяет достоверно восстановить
события. Такой уровень не выдаёт сигнал и сам не возобновляется.
Неверные или устаревшие котировки вызывают ошибку; checkpoint не продвигается.
Повторный запуск может восстановить обработку только из полной доступной истории.
Первый запуск новой пары устанавливает исходный checkpoint без рассылки истории.

При переходе со старой версии уровни с подтверждённой записью попытки отправки
считаются `completed`. Остальные старые регистрации получают `incomplete_history`:
старый ограниченный журнал не позволяет доказать, что сигнал ещё не отправлялся,
а старые установки не хранят признак возврата. Для нового наблюдения пользователь
явно удаляет и повторно добавляет нужный уровень. Новая версия сохраняет активные
ожидания и возврат между перезапусками без такого сброса.

## Доставка

Завершённый статус и намерение отправки сохраняются в ветку состояния ДО Telegram.
Ошибка сохранения блокирует отправку. Статус доставки:
`reserved` — намерение сохранено, результат неизвестен;
`confirmed` — Telegram подтвердил приём;
`unknown` — вызов завершился ошибкой, результат может быть неоднозначным.
Повторной попытки для этой регистрации нет.

Это защита от дублей, а не гарантированная доставка: при остановке между записью
и отправкой сообщение может потеряться. Telegram Bot API не обеспечивает
строгое exactly-once. Команды и offset также сохраняются до ответа.
Неисправное состояние и ошибки восстановления не заменяются пустым JSON.

## Тесты

Python 3.12:

```sh
python -m pip install -r requirements-liquidity.txt
python -m unittest discover -s tests -p 'test_liquidity*.py' -v
```

Тесты используют mock Telegram и источника котировок. Сквозные сценарии проверяют
настоящий BOS на заданных OHLC: оба направления выхода, разворот/продолжение,
возврат, перезапуск во время ожидания, терминальность сигнала и срока ожидания,
пропуски/неполное окно, тени и касания, миграцию старого состояния, ошибки доставки
и сохранения. Проверки Git используют локальный временный bare-репозиторий.
